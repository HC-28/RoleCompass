SECTION 1 — RATIONALE FOR CHANGES
═══════════════════════════════════════════════════════════════════════════════

PROBLEM IDENTIFIED IN v2.0:
Section 1 of the assessment is designed to measure RIASEC/psychometric dimensions —
behavioural preferences, not technical skill. The v2.0 questions contained domain-specific
jargon (schemas, stack traces, memory leaks, infrastructure clusters, pair programming,
empirical logs) that directly implied software knowledge.

This caused two failure modes:
  1. Candidates with software knowledge answered based on familiarity with the terms
     rather than their actual psychological preference, biasing routing toward software
     roles regardless of true fit.
  2. Candidates without software knowledge were confused by unfamiliar terms, causing
     invalid neutral responses (3/5 "Neutral" as a default) that depressed the
     discriminative power of the psychometric gate.

PRINCIPLE APPLIED IN v2.1:
Every Section 1 question must be answerable by a non-technical person. The question
text must probe the underlying psychological dimension — the trait — not the
technical context in which that trait might be expressed.

A Section 1 question PASSES review if:
  - A student who has never written code can still answer it meaningfully.
  - Replacing the word "software" with any other domain (medicine, art, accounting)
    still makes the question coherent.
  - The question does NOT mention: schemas, algorithms, APIs, code, frameworks,
    infrastructure, cloud, containers, compilers, commits, pipelines, stack traces,
    memory leaks, pair programming, logging, benchmarks.

SECTION 3 — COMPLETE REVISED QUESTION SET (SECTION 1, v2.1)
═══════════════════════════════════════════════════════════════════════════════

All questions use a 5-point Likert scale:
  1 = Strongly Disagree  2 = Disagree  3 = Neutral  4 = Agree  5 = Strongly Agree

─────────────────────────────────────────────────────────────────────────────
Q1 | Dimension: REALISTIC
─────────────────────────────────────────────────────────────────────────────
OLD (v2.0):
  "I enjoy spending time tinkering with technical tools, hardware, or systems and
   learning how they work by hands-on experimentation."

NEW (v2.1):
  "I would rather spend an afternoon physically building, repairing, or tinkering
   with something tangible, even if it does not turn out perfectly, than studying
   abstract concepts."

CHANGE REASON: Removed "technical tools, hardware, systems" — too domain-specific.
New version anchors on the behavioural trait (hands-on vs abstract) without requiring
technical context.

─────────────────────────────────────────────────────────────────────────────
Q2 | Dimension: REALISTIC + THINGS_PEOPLE
─────────────────────────────────────────────────────────────────────────────
OLD (v2.0):
  "When something technical breaks unexpectedly, I feel a strong urge to investigate
   and figure out what went wrong rather than waiting for someone else to fix it."

NEW (v2.1):
  "When an application or environment stops working — crashing with an obscure error
   or behaving unexpectedly — I feel a strong pull to investigate the root cause myself."

CHANGE REASON: Narrowed only slightly — "application or environment" is more specific
than "something technical" but avoids deep domain jargon. Retained for v2.1 and flagged
for further review if non-technical candidate confusion persists.

NOTE FOR v2.2: Consider replacing "crashing with an obscure error" with "fails without
an obvious reason" to fully remove technical reference.

NEW (v2.1):
  "I enjoy reading in-depth manuals, technical specifications, and system internals

CHANGE REASON: v2.0 question was acceptable but "whitepapers and research papers" is
domain-adjacent. New version slightly better but still contains "technical specifications"

NEW (v2.1):

CHANGE REASON: Equivalent strength. New phrasing "no standard textbook solution"
explicitly frames the dimension (ambiguity vs structure) without technical jargon.
APPROVED — no further change needed.

NEW (v2.1):

SECTION 4 — NUMBERING AND STRUCTURE FIXES
═══════════════════════════════════════════════════════════════════════════════

Issue in v2.0:
  - Question numbering in Section 2 reset to "Evaluation Question 1" at the start
    of each sub-section (domain). This was confusing for candidates and implied
    a restart of the assessment.

Fix in v2.1:
  - All questions are numbered cumulatively across the entire assessment.
  - Example: Section 1 Q1-Q16, Section 2 Q17-Q56 (adaptive: Q17-Q36 typically),
    Section 3 Q37-Q40, Section 4 Q41-Q44.
  - The question number displayed to the candidate never resets.

Issue in v2.0:
  - Section 2 sub-sections (domains) were not labelled for the candidate.
  - Candidates could not tell which area they were being assessed on.

Fix in v2.1:
  - A "Section Banner" is displayed above each question showing:
    - Section number (1, 2, 3, or 4)
    - Section name (e.g., "Technical Core Assessment")
    - Sub-section name within Section 2 (e.g., "Server Logic", "Data Storage")

Issue in v2.0:
  - The Q2 skip (adaptive skip) was applied at the batch level, not the question level.
    Because Section 2 served 4 questions per API call, Q1 and Q2 of the same domain
    were often shown together, making the skip rule ineffective.

Fix in v2.1:
  - Section 2 now serves exactly 1 question per API call.
  - When a candidate answers Q1 of a domain with an extreme score (1, 2, 4, or 5),
    Q2 of that domain is skipped entirely, and the next API call delivers Q1 of the
    next domain.
  - This was verified in end-to-end testing: answering Server Logic Q1 with Strongly
    Agree caused the system to return Data Storage Q1 next (skipping Server Logic Q2).

ADAPTIVE SKIP RULE:
  If Q1 answer is ≤ 2 (Disagree/Strongly Disagree) OR ≥ 4 (Agree/Strongly Agree):
    → Domain is considered resolved. Q2 is skipped.
  If Q1 answer is = 3 (Neutral):
    → Domain is ambiguous. Q2 is asked to confirm/deny.

TYPICAL OUTCOMES:
  - All domains extreme: 20 questions answered (min)
  - No domain extreme: 40 questions answered (max)
  - Real-world average: ~22–28 questions answered
